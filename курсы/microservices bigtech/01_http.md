## protocol buffer

==**`Что не так c JSON?`**==
- Динамическая схема
- Медленный парсинг
	строка десериализация (теги) в структуре golang
	easyJSON от mail (костыль)

- Отсутствие типизации
	считали в интах потом во флотах
	
- Большой размер данных
	тело - текст

**==`Плюсы protobuf`==**
- Меньший размер
	бинарный вид (сжатие)
	не передает имена полей
	
- Типизация
	позволяет жестко фиксировать контракт
	
- Схема данных
	обязательные/необязательные поля...
	
- Разные языки
	можно сгенерировать под разные языки

==**`Типы данных protobuff`**==
- double, float
- int32, int64
- uint32, uint64
- sint32, sint64
	инт такой положительный и отрицательный только оптимизирован для отрицательных значений чисел
	
- fixed32, fixed64
	оптимизирован для больших значений
	
- bооl, string, bytes(сырые данные)
- google nullable type
	все поля в protobuff опциональны.
	позволяет различить нулевое поле от изменения клиентом на 0

==**`message в protobuff = структура в го`**==

==`reserved`== резервирует
убираем поле и делаем reserved. пометит что поле было. никуда не распакует. 
используют для удаления 
либо для добавления чего-либо в будущем

младшие 3 бита кодируют тип данных
старшие 5 бит кодируют номер поля id
если понадобится больше байт поле то они добавятся

## gRPC

==**`Что не так с HTTP?`**==(1.1)
- создает новое tcp-соединение на запрос
	конечно можно сказать серверу с помощью ==`keep alive`== заголовка чтобы не закрывал соединение, но по дефолту нет и так расходует достаточно ресурсов
	
- head of blocking
	особенность архитектуры http1.1 сводится к тому что при заказе файлов с сервера
	нельзя параллельно загружать CSS
	
- не сжимает заголовки
	передает как текст
	
- нет server push
	по дефолту работает как запрос -> ответ
	sse
	сокеты

==**`Фишки http2`**==
- одно tcp соединение
	гораздо полно утилизировать ресурсы
	
- потоковая передача данных
	без вебсокетов можно настроить непрерывное соединение
	стриминговые ручки
	
- бинарный протокол
	тело в бине, сжатие данных
	не получится перехватить json
	
- сервер может обратиться к клиенту
	запрашиваем чтото у сервера, оставляем непрерывный коннект, сервер додумает и выплюнет клиенту
	
- сжатие заголовков
	в http1 было сжатие заголовков но не безопасно. например cookies могли передаваться


можно сделать на нескольких ЯП

Декларация объявления API

==`Get`== - название эндпоинта
==`GetRequest`== - название запроса. название эндпоинта+Request
==`GetResponse`== - название ответа. название эндпоинта+Response
```
//ключевое слово service - название
//внутри эндпоинты/ручки/точки входа API
service UserV1 {
	rpc Get(GetRequest) returns (GetResponse);
}

message UserInfo {
	int64 id = 1;
	string name 2;
	bool is_human = 3;
}

message GetRequest {
	int64 id = 1; // на вход id
}

message GetResponse {
	UserInfo info = 1; // возвращаем инфу о поль-ле UserInfo
}
```

у grpc есть ==несколько вариантов ручек==: 
- один запрос, один ответ
	унарное взаимодействие
```
rpc Send(Message) returns (Result);
```

- один запрос, поток ответов
	стриминговое 
	пагинацией выдает
```
rpc Send(Message) returns (stream Result);
```

- поток запросов, один ответ
	стримим, потом сервер дает единый ответ 
```
rpc Send(stream Message) returns (Result);
```

- поток запросов, поток ответов
	двусторонний коннект
	дуплексное соединение
```
rpc Send(stream Message) returns (stream Result);
```
